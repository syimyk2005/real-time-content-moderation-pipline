# StreamGuard — техническое задание

Real-time система модерации комментариев. Поток комментариев проходит через Kafka, воркеры анализируют текст через LLM (токсичность / спам / тональность), результаты агрегируются и показываются на live-дашборде.

**Стек:** Java 21 (LTS) + Spring Boot 3.x, Apache Kafka, PostgreSQL, Redis, LLM (Ollama локально или дешёвый API), WebSocket, Prometheus + Grafana, Docker Compose, Testcontainers для тестов, Maven.

---

## Порядок разработки (по этапам)

Не строй всё сразу. Иди снизу вверх, на каждом этапе система должна работать целиком.

1. **Монолит-скелет** — один сервис: принять коммент по REST → синхронно позвать LLM → сохранить в PostgreSQL → показать статистику. Цель: убедиться, что анализ работает.
2. **Вставить Kafka** — разнести на ingest-service и moderation-worker, между ними топик `comments.incoming`.
3. **stats-service + дашборд** — второй топик `comments.moderated`, агрегация, WebSocket, простой live-дашборд.
4. **Масштабирование** — несколько воркеров (consumer group), Redis (rate limit + кэш решений).
5. **Надёжность** — retry, dead letter queue, идемпотентность, батчинг вызовов LLM.
6. **Observability + упаковка** — Prometheus + Grafana, всё поднимается одной командой через Docker Compose. Load-generator для нагрузочного теста.

---

## Сервис 1: ingest-service

Входная дверь системы. Быстро принимает комментарии и кладёт в очередь, сам анализом не занимается.

**Что делает:**
- REST-эндпоинт `POST /comments`, принимает JSON `{ "userId": 123, "text": "..." }`.
- Валидирует: текст не пустой, не длиннее лимита (например 5000 символов), поля на месте.
- Rate limiting через Redis: не больше N комментов в минуту с одного userId, иначе `429`.
- Присваивает `commentId` (UUID), кладёт событие в Kafka топик `comments.incoming`.
- Сразу отвечает `202 Accepted` с `commentId` и статусом `PENDING`. НЕ ждёт результата анализа.
- (Опционально) `GET /comments/{id}` — узнать текущий статус комментария.

**Технически:** Spring Boot + Spring Web + Spring Kafka (producer) + Spring Data Redis. Самый простой сервис, начинай с него.

**Критерий готовности:** отправляешь POST — получаешь мгновенный ответ с id, в Kafka появляется сообщение.

## Сервис 2: moderation-worker

Мозг системы. Слушает очередь, анализирует каждый коммент через LLM, выносит вердикт.

**Что делает:**
- Kafka consumer, слушает `comments.incoming` (в составе consumer group — чтобы несколько экземпляров делили нагрузку).
- По каждому комменту вызывает LLM: оценка токсичности (0–100), спам (да/нет), тональность (positive/negative/neutral).
- Применяет правила решения, например: токсичность > 80 → `REJECTED`; спам → `REJECTED`; токсичность 50–80 → `NEEDS_REVIEW`; иначе → `APPROVED`.
- Пишет результат в PostgreSQL и отправляет событие в топик `comments.moderated`.

**Ключевые технические фишки (закладывай постепенно):**
- **Виртуальные потоки Java 21** — вызов LLM это ожидание сети, виртуальные потоки держат тысячи таких операций дёшево. Включается настройкой в Spring Boot 3.
- **Кэш решений в Redis** — одинаковый текст (частый спам) не гонять через LLM повторно, ключ по хэшу текста.
- **Батчинг** — собирать по 10–20 комментов и слать в LLM одним запросом, экономит время и деньги.
- **Идемпотентность** — по `commentId`, повторная обработка не должна дублировать запись.
- **Retry + DLQ** — если LLM упал, повторить; после N неудач отправить в топик `comments.dlq`.

**Технически:** Spring Boot + Spring Kafka (consumer) + Spring Data JPA + Spring Data Redis + HTTP-клиент к LLM (или Spring AI).

**Критерий готовности:** запускаешь 2–3 воркера, кидаешь поток комментов — они разбираются параллельно, вердикты пишутся в базу.

## Сервис 3: stats-service

Считает статистику по потоку и пушит её на дашборд в реальном времени.

**Что делает:**
- Kafka consumer, слушает `comments.moderated`.
- Агрегирует метрики: сколько approved/rejected/needs_review за минуту, средняя токсичность, доля спама, топ нарушителей.
- Быстрые счётчики держит в Redis (инкременты).
- Через WebSocket пушит обновления на дашборд.
- (Опционально) REST-эндпоинты для истории и для очереди `NEEDS_REVIEW`.

**Технически:** Spring Boot + Spring Kafka (consumer) + Spring WebSocket + Spring Data Redis.

**Критерий готовности:** при потоке комментов на дашборде в реальном времени бегут счётчики и графики.

## Дашборд (фронт)

Живая панель модератора. Можно на чистом HTML + JS + Chart.js, без тяжёлого фреймворка — суть в бэкенде.

**Что показывает:**
- Живые графики: комментов/сек, распределение approved/rejected/review, средняя токсичность по времени.
- Очередь `NEEDS_REVIEW` с кнопками «одобрить / отклонить» (ручная модерация).
- Подключение к stats-service через WebSocket.

## load-generator (тестовый инструмент, НЕ часть системы)

Прикидывается пользователями, чтобы гонять систему под нагрузкой. Живёт снаружи, на месте реальных юзеров.

**Что делает:**
- Читает строки из датасета (Jigsaw Toxic Comments с Kaggle — реальные размеченные комментарии).
- В цикле шлёт их в `POST /comments` со случайными паузами, интенсивность настраивается.
- Для «официального» нагрузочного теста — Gatling (на JVM, строит графики latency/throughput, результаты в README).

**Бонус:** раз у датасета есть настоящие метки токсичности, можно посчитать accuracy своей системы — сравнить вердикты с эталоном. Отличная строчка: «замерял качество на размеченном датасете».

## Топики Kafka

| Топик | Кто пишет | Кто читает | Содержимое |
|-------|-----------|------------|------------|
| `comments.incoming` | ingest-service | moderation-worker | новый коммент на обработку |
| `comments.moderated` | moderation-worker | stats-service | результат анализа + вердикт |
| `comments.dlq` | moderation-worker | (ручной разбор) | не обработанные после retry |

## Схема БД (PostgreSQL)

Таблица `comments`:

- `id` (UUID, PK) — commentId
- `user_id` (bigint)
- `text` (text)
- `status` (varchar) — PENDING / APPROVED / REJECTED / NEEDS_REVIEW
- `toxicity_score` (int) — 0–100
- `is_spam` (boolean)
- `sentiment` (varchar) — positive / negative / neutral
- `created_at` (timestamp)
- `processed_at` (timestamp)

Индексы по `status` и `created_at` — для быстрой выборки очереди на ревью и статистики.

## LLM

Для пета не обязателен платный API.

- **Ollama локально** (модель Llama 3 или Qwen) — бесплатно, плюс строчка «local LLM deployment, no external dependencies».
- Или дешёвая модель по API — токсичность/спам не требуют самой мощной модели.
- **Spring AI** — официальный фреймворк для интеграции LLM в Spring-мир, ложится в твой стек.

Промпт: попроси модель вернуть строго JSON вида `{ "toxicity": 0-100, "spam": true/false, "sentiment": "..." }`, чтобы легко распарсить.

## Тестирование

- **Корректность** — интеграционные тесты через Testcontainers (настоящие Kafka + PostgreSQL в Docker). Заведомо токсичный текст → REJECTED, нормальный → APPROVED.
- **Точность** — прогнать размеченный датасет, посчитать accuracy.
- **Нагрузка** — load-generator + Gatling, смотреть в Grafana: throughput держится, latency не растёт, добавил воркер → пропускная способность выросла.
- **Отказоустойчивость** — выключить LLM (сообщения в retry → DLQ), убить воркер (Kafka rebalance), послать дубль commentId (одна запись в базе).

---

## Итоговые метрики для наблюдения (Prometheus + Grafana)

- Throughput: комментов/сек.
- Latency обработки одного коммента.
- Доля rejected / needs_review.
- Задержка ответа LLM.
- Размер DLQ.

## Что это даст в резюме (честно, потому что реально сделано)

Event-driven микросервисы на Kafka, горизонтальное масштабирование через consumer groups, виртуальные потоки Java 21, real-time стриминг через WebSocket, LLM-интеграция с батчингом и кэшированием, resilience (retry, DLQ, идемпотентность), observability (Prometheus + Grafana), Redis для кэша и rate limiting, интеграционные тесты через Testcontainers, нагрузочное тестирование через Gatling, всё в Docker Compose.
